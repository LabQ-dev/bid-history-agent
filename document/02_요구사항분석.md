# 02. 요구사항 분석 — 입찰참가 이력 검색 에이전트

## 1. 기능 요구사항 (Functional Requirements)

### FR-1. 검색 조건

| ID | 요구사항 | 비고 |
|---|---|---|
| FR-1.1 | 회사명으로 검색할 수 있다 | 부분일치. `주식회사`, `(주)`, `(유)` 등 법인격 표기와 공백은 무시하고 비교 |
| FR-1.2 | 사업자등록번호로 검색할 수 있다 | 하이픈 유무 무관 (숫자만 비교) |
| FR-1.3 | 대표자명을 추가 조건으로 줄 수 있다 | 회사명/사업자번호와 **AND** 조건. 회사명·사업자번호는 서로 **OR** |
| FR-1.4 | 조회 기간을 지정한다 (개찰일 기준, YYYYMMDD) | 필수 입력 |
| FR-1.5 | 업무구분을 선택할 수 있다 | 물품/공사/용역/외자, 기본 전체 |
| FR-1.6 | 공고명 키워드로 스윕 범위를 줄일 수 있다 | API 호출량 절약 목적 (선택) |
| FR-1.7 | 공고번호로 직접 조회할 수 있다 | 해당 공고의 참가업체 전체 순위표. 기간 불필요 |

### FR-2. 검색 결과

| ID | 요구사항 |
|---|---|
| FR-2.1 | 매칭된 참가 건마다 공고정보(공고번호·공고명·발주기관·개찰일시)와 업체정보(업체명·대표자·사업자번호)를 제공한다 |
| FR-2.2 | 개찰순위(opengRank), 투찰금액을 제공한다. 1위 = 낙찰(예정)자 |
| FR-2.3 | 협상에 의한 계약 건은 기술평가점수·입찰가격점수·종합평가점수를 함께 제공한다 |
| FR-2.4 | 1위(낙찰) 행은 표와 엑셀에서 하이라이트한다 |
| FR-2.5 | 결과는 개찰일시 → 순위 순으로 정렬한다 |
| FR-2.6 | 각 매칭 건에 대해 해당 공고의 1위 업체(낙찰자) 정보를 함께 보여준다 |

### FR-3. 출력/인터페이스

| ID | 요구사항 |
|---|---|
| FR-3.1 | 웹 화면에서 검색 조건 입력 → 검색 → 결과 표 확인이 가능하다 |
| FR-3.2 | 검색 진행 상황(스윕/상세조회 로그)을 실시간으로 표시한다 |
| FR-3.3 | 결과를 XLSX 파일로 다운로드할 수 있다 |
| FR-3.4 | CLI에서도 동일한 검색이 가능하며 콘솔 표 + XLSX/CSV 저장을 지원한다 |

### FR-4. 일일 수집 (collector)

| ID | 요구사항 |
|---|---|
| FR-4.1 | 매일 지정 시각(기본 06:00)에 전날 개찰완료 공고의 참가업체 데이터를 수집해 캐시에 적재한다 |
| FR-4.2 | 특정일 수집, 기간 지정 소급 수집(백필)을 지원한다 |
| FR-4.3 | 이미 수집된 공고는 건너뛴다 (반복 실행 안전 = 멱등) |
| FR-4.4 | 일일 호출 한도(기본 800회) 도달 시 중단하고, 다음 실행 때 이어서 수집한다 |

## 2. 비기능 요구사항 (Non-Functional Requirements)

### NFR-1. API 트래픽 관리 (최우선 제약)

- 개발계정 한도 **1,000회/일**, 공고 1건당 상세조회 1회 필요
- **NFR-1.1** 상세조회 결과는 SQLite에 영구 캐시하고, 캐시 히트 시 API를 호출하지 않는다
- **NFR-1.2** 웹 검색의 상세조회는 기본 300회, 최대 500회로 제한한다 (수집기 몫을 남김)
- **NFR-1.3** 한도 초과(오류코드 22)를 감지하면 즉시 중단하고, 재실행 시 캐시 이후부터 이어간다
- **NFR-1.4** 초당 호출 간격을 두어 TPS 제한(30 TPS)에 대응한다

### NFR-2. 안정성

- **NFR-2.1** API 호출 실패 시 지수 백오프로 최대 3회 재시도한다
- **NFR-2.2** 개별 공고 조회 실패는 경고 로그 후 계속 진행한다 (전체 중단 금지)
- **NFR-2.3** 게이트웨이 오류·나라장터 자체 오류 응답을 구분해 사용자에게 원인을 알린다
- **NFR-2.4** 조회기간 1개월 제한에 걸리지 않도록 30일 단위로 분할 조회한다

### NFR-3. 보안

- **NFR-3.1** 인증키(G2B_SERVICE_KEY)는 `.env`로 관리하고 코드/HTML에 넣지 않는다
- **NFR-3.2** 로그·오류 메시지에서 인증키를 마스킹한다
- **NFR-3.3** 외부 접속 허용(WEB_HOST=0.0.0.0) 시 비밀번호(Basic Auth)를 설정한다.
  미설정 시 경고를 출력한다 (무단 사용에 의한 한도 소진 방지)
- **NFR-3.4** 비밀번호 비교는 타이밍 공격에 안전한 방식(hmac.compare_digest)을 쓴다

### NFR-4. 운영/배포

- **NFR-4.1** 웹 서버는 외부 패키지 없이 파이썬 표준 라이브러리로 동작한다
- **NFR-4.2** Docker(web + collector 컨테이너)와 systemd 배포를 지원한다
- **NFR-4.3** 데이터는 단일 파일(cache.db) — 이 파일만 복사하면 서버 이전 완료
- **NFR-4.4** 동시 검색은 1건만 허용한다 (진행 중 재요청 시 409 응답) — 팀 공용
  사용 시 한도 폭주 방지

### NFR-5. 사용성

- **NFR-5.1** 비개발자 팀원이 브라우저만으로 사용할 수 있어야 한다
- **NFR-5.2** 검색이 오래 걸릴 수 있으므로 진행 로그를 보여 대기 불안을 줄인다
- **NFR-5.3** 한도 도달·중단 시 "내일 재실행하면 이어서 조회" 등 다음 행동을 안내한다

## 3. 외부 인터페이스 요구사항

- **데이터 출처**: 조달청_나라장터 낙찰정보서비스 (공공데이터포털 15129397)
  - Endpoint: `https://apis.data.go.kr/1230000/as/ScsbidInfoService`
  - 사용 오퍼레이션:
    - `getOpengResultListInfo{Thng,Cnstwk,Servc,Frgcpt}` — 업무구분별 개찰결과 목록
    - `getOpengResultListInfoOpengCompt` — 공고별 참가업체 순위/평가점수
- 상세 명세: 프로젝트 루트의 `02_나라장터_낙찰정보서비스_API명세.docx` 참고

## 4. 데이터 요구사항

| 항목 | 내용 |
|---|---|
| 저장소 | SQLite 단일 파일 (`cache.db`, 도커에서는 `./data/cache.db`) |
| 테이블 | `participants(key TEXT PRIMARY KEY, data TEXT)` |
| 키 | `bidNtceNo\|bidNtceOrd\|bidClsfcNo\|rbidNo` (공고번호·차수·분류·재입찰번호 조합) |
