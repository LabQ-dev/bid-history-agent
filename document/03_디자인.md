# 03. 디자인 — 아키텍처 및 화면 설계

## 1. 시스템 아키텍처

```
                        ┌─────────────────────────────────────────┐
                        │  공공데이터포털 (조달청 낙찰정보서비스)      │
                        │  ScsbidInfoService OpenAPI              │
                        └───────────────▲─────────────────────────┘
                                        │ HTTPS (인증키, 일 1,000회 한도)
              ┌─────────────────────────┴──────────────────────┐
              │                bid_history 패키지                │
              │  api.py     : OpenAPI 클라이언트                 │
              │               (페이징·재시도·TPS간격·30일 분할)    │
              │  search.py  : 스윕 → 상세조회 → 로컬 필터          │
              │  report.py  : 콘솔 표 / CSV / XLSX               │
              └───▲──────────────▲──────────────▲───────────────┘
                  │              │              │
        ┌─────────┴───┐  ┌───────┴──────┐  ┌────┴─────────┐
        │  web.py     │  │  main.py     │  │ collector.py │
        │  웹 서버     │  │  CLI         │  │ 일일 수집기    │
        │  (표준lib)   │  │              │  │ (06시 데몬)   │
        └─────▲───────┘  └──────────────┘  └────┬─────────┘
              │ HTTP :8931                       │
        ┌─────┴───────┐              ┌──────────▼──────────┐
        │ index.html  │              │  cache.db (SQLite)   │◀── web/CLI도 읽고 씀
        │ 브라우저 UI  │              │  participants 테이블  │
        └─────────────┘              └─────────────────────┘
```

**설계 원칙**
- 검색 로직은 `bid_history` 패키지 한 곳에만 두고, 웹/CLI/수집기가 공유한다.
- 웹 서버는 표준 라이브러리(`http.server`)만 사용 — 배포 의존성 최소화.
- 캐시는 3개 진입점(웹·CLI·수집기)이 같은 `cache.db`를 공유하여, 누가 조회하든
  다음 사용자는 API를 아낀다.

## 2. 핵심 흐름 설계 (검색)

```
사용자 입력 (회사명/사업자번호[+대표자명], 기간, 업무구분, 키워드)
  │
  ▼ ① 스윕 (sweep_bids)
업무구분별 getOpengResultListInfo* 를 30일 단위로 분할 호출
  → "개찰완료" 상태만 통과, 키워드 필터, 중복 제거(공고번호+차수+분류+재입찰)
  │
  ▼ ② 공고별 상세 (search)
공고 키로 cache.db 조회 → 미스일 때만 getOpengResultListInfoOpengCompt 호출 후 캐시 저장
  → 호출 한도(max_detail_calls) 도달 시 중단 + "이어서 조회" 안내
  │
  ▼ ③ 로컬 필터 (Query.matches)
(회사명 부분일치 OR 사업자번호 일치) AND 대표자명 부분일치
  → 매칭 건에 해당 공고 1위(낙찰자) 정보 첨부
  │
  ▼ ④ 출력
개찰일시 → 순위 순 정렬 → 웹 표 / 콘솔 표 / XLSX·CSV (1위 행 하이라이트)
```

**문자열 정규화 규칙** (search.py)
- 회사명: `주식회사`, `(주)`, `(유)`, `유한회사`, `합자회사` 등 법인격 표기와 공백 제거 후 소문자 비교
- 사업자번호: 숫자만 남겨 비교
- 대표자명: 공백 제거 후 부분일치

## 3. 웹 서버 API 설계 (web.py)

| 메서드 | 경로 | 역할 | 응답 |
|---|---|---|---|
| GET | `/` | 검색 화면(index.html) 서빙 | HTML |
| POST | `/api/search` | 검색 시작 (백그라운드 스레드) | `{ok}` / 진행 중이면 409 |
| GET | `/api/status` | 진행 로그·상태·결과 폴링 | `{state, logs, error, rows}` |
| GET | `/api/download` | 최근 결과 XLSX 다운로드 | xlsx 바이너리 |
| GET | `/api/bid?no=공고번호` | 공고별 참가업체 순위표 (캐시에서만) | `{found, rows}` |

**동작 방식 설계 결정**
- 검색은 수 분이 걸릴 수 있으므로 **비동기 작업 + 폴링** 구조:
  POST가 즉시 반환하고, 프런트가 `/api/status`를 주기 폴링해 로그와 결과를 갱신.
- 작업 상태는 전역 1슬롯(`job`) — 동시 검색 1건 제한 (API 한도 보호, NFR-4.4).
- 진행 로그는 `logging.Handler`를 job에 연결해 검색 로직 수정 없이 수집 (최근 200줄 유지).
- 인증: `WEB_PASSWORD` 설정 시 HTTP Basic Auth (브라우저 기본 로그인창 활용,
  별도 로그인 페이지 불필요).

## 4. 화면 설계 (index.html)

단일 페이지, 카드 3개가 세로로 쌓이는 구조. (실제 화면: `서비스화면_전체.png`, `서비스화면_검색폼.png`)

```

│  [로고]  입찰참가 이력 검색                  │  ← 헤더
├──────────────────────────────────────────┤
│  검색 폼 (2열 그리드, 모바일 1열)            │
│   회사명* | 사업자등록번호*                  │
│   대표자명 | 조회기간(from~to)*             │
│   업무구분 ☑물품 ☑공사 ☑용역 ☑외자          │
│   공고명 키워드 | 최대 호출수                │
│   [        검  색        ]                │

│  진행상황 카드 (검색 중 표시)                │
```

**스타일 가이드**
- 폰트: Apple SD Gothic Neo / Malgun Gothic (시스템 한글 폰트)
- 색: 주조 파랑 `#1a73e8`(검색 버튼·포커스), 다운로드 초록 `#137333`,
  오류 빨강 배경 `#fce8e6`, 페이지 배경 `#f4f6f8`, 카드 흰색 + 12px 라운드
- 반응형: 700px 이하에서 폼 1열 전환

## 5. 데이터 설계

SQLite `cache.db` (WAL 모드 — 조회와 수집 동시 허용). `key = "공고번호|차수|입찰분류번호|재입찰번호"`.

| 테이블 | 내용 |
|---|---|
| `bids` | 공고 메타 (목록 API ①) — key PK, 공고번호, 업무구분, 공고명, 개찰일시, 수요기관, 공고기관, 참가업체수, 진행구분 |
| `participants` | 참가업체 1명 = 1행 (개찰완료 API ②) — key, 순위, 사업자번호, 업체명, 대표자, 투찰금액, 투찰률, 기술/가격/종합점수, 비고, 정규화 컬럼(normNm, normBizno) |
| `fetched` | 참가업체 명단 수집 완료된 공고 key (참가 0명 공고 구분용) |
| `swept` | 업무구분×일자별 공고 목록 스윕 완료 기록 (오늘/미래는 기록하지 않음) |
| `companies` | 업체 검색 팝업용 고유 회사 목록 — normBizno PK, 업체명, 대표자, normNm |

- 인덱스: `bids(opengDt, bidNtceNo)`, `participants(key, normNm, normBizno)`
- 검색은 `participants ⨝ bids` 조인 SQL로 수행 — 수집된 기간은 API 호출 0회
- 조인은 항상 key 기준 (공고번호 단독 금지 — 재공고·재입찰·단가계약 분류 구분)
- 개찰완료 데이터는 **불변**이므로 TTL/무효화가 필요 없다. 단, 조달청이 개찰결과를
  사후 등록하는 경우가 있어 수집기 데몬이 최근 7일을 매일 재확인한다.
- 도커 볼륨: `./data/cache.db` — 이 파일 하나가 전체 상태 (마이그레이션 = 파일 복사).

## 6. 오류 처리 설계

| 상황 | 처리 |
|---|---|
| 네트워크/일시 오류 | 지수 백오프(2ⁿ초) 최대 3회 재시도 |
| 일일 트래픽 초과 (코드 22) | 즉시 중단, "내일 재실행 시 이어서" 안내 (재시도 무의미) |
| 나라장터 자체 오류 (resultCode ≠ 00) | 오퍼레이션명 + 코드 + 메시지로 예외 |
| 개별 공고 조회 실패 | 경고 후 빈 결과로 캐시, 전체 검색은 계속 |
| 조회기간 1개월 초과 제한 | 사전에 30일 단위 분할로 회피 |
| 인증키 노출 위험 | 모든 로그/예외 메시지에서 키를 `***KEY***`로 마스킹 |
