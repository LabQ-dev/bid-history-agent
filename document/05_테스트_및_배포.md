# 05. 테스트 및 배포

## 1. 테스트

> 자동화 테스트 코드는 없으며, 아래 수동 시나리오로 검증한다.

### 1.1 기능 테스트 시나리오

| # | 시나리오 | 기대 결과 |
|---|---|---|
| T-1 | 회사명(부분, `(주)` 포함/제외)으로 검색 | 법인격 표기와 무관하게 동일 결과 |
| T-2 | 사업자번호(하이픈 포함/제외)로 검색 | 동일 결과 |
| T-3 | 회사명 + 대표자명 검색 | 대표자명 불일치 건은 제외 (AND 동작) |
| T-4 | 조건 없이 검색 | "하나 이상 입력" 오류 안내 |
| T-5 | 기간 없이 검색 | "조회 기간 입력" 오류 안내 |
| T-6 | 1개월 초과 기간 검색 | 30일 분할 조회 로그 확인, 오류 없이 완료 |
| T-7 | 공고번호 직접 조회 (`--bid-no`, `/api/bid`) | 참가업체 전체 순위표, 순위 오름차순 |
| T-8 | 결과 표 1위 행 | 웹 표·엑셀 모두 하이라이트 |
| T-9 | 엑셀 다운로드 | 한글 파일명(검색결과.xlsx) 정상, 내용 = 화면 표 |
| T-10 | 검색 진행 중 재검색 | 409 "이미 검색이 진행 중입니다" |
| T-11 | 협상계약 건 | 기술/가격/종합 점수 표시 |

## 2. 배포

### 2.1 배포 옵션 비교

| 방식 | 대상 | 특징 |
|---|---|---|
| Docker Compose (권장) | 서버/공용 PC | web + collector 컨테이너, 재부팅 자동 시작 |
| systemd | 리눅스 공용 PC | `deploy/bid-history.service`, 5초 자동 재시작 |
| 직접 실행 | 개인 PC | `uv run python web.py`, 터미널 켜둔 동안만 |

### 2.2 Docker 배포

```bash
cp .env.example .env    # G2B_SERVICE_KEY, WEB_PASSWORD 입력
docker compose up -d --build
docker compose logs -f collector   # 수집 로그 확인
```

- `web` 컨테이너: 검색 화면 (:8931)
- `collector` 컨테이너: 매일 06시 어제치 개찰결과 자동 수집 (`--daemon`)
- 데이터 볼륨: `./data/cache.db`

### 2.3 systemd 배포 (리눅스)

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
git clone https://github.com/LabQ-dev/bid-history-agent.git ~/bid-history-agent
cd ~/bid-history-agent && uv sync
# .env: G2B_SERVICE_KEY, WEB_HOST=0.0.0.0, WEB_PASSWORD

sed "s/USERNAME/$(whoami)/g" deploy/bid-history.service | sudo tee /etc/systemd/system/bid-history.service
sudo systemctl daemon-reload
sudo systemctl enable --now bid-history
sudo ufw allow 8931          # 방화벽 사용 시
```

### 2.4 배포 체크리스트

- [ ] `.env`에 `G2B_SERVICE_KEY` 설정 (Decoding 키)
- [ ] 외부 접속 시 `WEB_HOST=0.0.0.0` + `WEB_PASSWORD` 반드시 설정
- [ ] 백필: 과거 검색이 필요하면 `collector.py --from ... --to ...` 미리 실행
- [ ] 수집 시각/한도 확인 (`COLLECT_HOUR=6`, `COLLECT_MAX_CALLS=800`)
- [ ] 팀원에게 접속 주소(`http://<IP>:8931`)와 비밀번호 공유
- [ ] (운영 전환) 공공데이터포털 활용사례 등록으로 트래픽 한도 증가 신청

### 2.5 운영

| 작업 | 방법 |
|---|---|
| 코드 업데이트 | `git pull` 후 `docker compose up -d --build` 또는 `systemctl restart bid-history` |
| 서버 이전 | 레포 클론 + `./data/cache.db`(또는 cache.db) 복사 → 끝 |
| 백업 | `cache.db` 파일 주기 복사 (개찰 데이터는 재수집 가능하나 API 호출 절약 차원) |
| 로그 | `docker compose logs -f` / `journalctl -u bid-history -f` |
| 장애 시 | web은 무상태(캐시 제외)라 재시작으로 복구. 수집 실패는 다음 날 자동 재시도 |

## 3. 알려진 한계

- 개발계정 한도(1,000회/일)로 넓은 기간의 첫 검색은 며칠에 나눠 진행됨
  (공공데이터포털 활용사례 등록으로 운영계정 전환 시 트래픽 한도 증가)
- 검색은 동시 1건만 가능 (진행 중 재요청 시 409)
- 개찰 전(진행 중) 공고는 검색 대상이 아님 — 개찰완료 건만 조회
